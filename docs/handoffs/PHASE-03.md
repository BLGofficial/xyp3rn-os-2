HANDOFF — Phase 3 complete

- **Built:**
  - pgvector (`extensions` schema) with 384-dim embedding columns and HNSW cosine indexes on `canonical_prompts` and `sources` (migration `20260924100000_embeddings.sql`).
  - The `xyp_match_knowledge()` vector search function.
  - Two roles: `xyp_embedder` (writes the 5 embedding columns only) and `xyp_runtime` (read-only).
  - The embedding pipeline (`knowledge/vector-retrieval/*`, `pnpm embed`), idempotent by a hash of model + input.
  - The Context Engine (`core/context-engine/*`, `pnpm context "<q>"`): vector hits plus 1-hop graph expansion over `relations` and the prompt→module foreign key. Every item carries its row reference, score, reasons, a readable `why`, and its source.
  - An LRU cache: 256 entries, 15-minute TTL, keyed on a knowledge generation value that changes on any canonical, source or relations write.
  - **Real run:** 31 prompts and 1 source embedded, 0 truncated. The worked example with scores is in `docs/proofs/PHASE-03-retrieval-example.txt`.
- **Key decisions:**
  - The user chose gte-small run locally (it matches Supabase's built-in Edge Function model; no key needed; deterministic), one vector per row, and an in-process LRU cache.
  - The embedded text is built from structure: title, role, task and constraints.
  - The ranking formula is explicit: direct hit = cosine similarity; neighbour = parent × weight. Weights: `depends_on` 0.8 out / 0.6 in, `precedes` 0.7 / 0.7, `module_of` (FK) 0.6 out, `derived_from` 0.5 out and 0 in, since a source fans out to everything derived from it. Unknown predicates are skipped and reported.
- **Deviations from spec:**
  - **Split result quotas:** 8 direct hits plus up to 4 graph-only neighbours, instead of a single top-N. Measured gte-small similarities cluster in 0.85–0.92, so any neighbour (≤ 0.8 × parent) always ranked below every direct hit and expansion never surfaced. Scores are unchanged; inclusion is by quota. A test covers this.
  - **Prompt→module link:** the Context Engine treats `canonical_prompts.module_id` as an implicit `module_of` edge instead of duplicating it into `relations`.
  - **Pipeline:** embeddings are generated by a separate pipeline step (`pnpm embed`), not as part of ingestion.
- **Open flags:**
  - **Retrieval sharpness is weak on this corpus.** The top 8 in the worked example are separated by 0.028, and the off-topic "Phase 8 Songwriting" prompt ranks #3 on a governance question. Candidates to fix it: hybrid lexical search (Postgres `tsvector`) or a reranker. Not added.
  - **Truncation:** 0 rows are truncated today, but a row over 512 tokens is truncated. That is recorded in `embedding_truncated`, not hidden.
  - **Cost of the generation key:** computing it costs one small query per call, even on a cache hit.
  - **Embed transaction length:** the embed pipeline holds one transaction across model inference. That's fine at 32 rows; batch it if the corpus grows.
  - **Skipped build scripts:** pnpm ignores the onnxruntime-node and protobufjs build scripts (`pnpm.ignoredBuiltDependencies`). Verified working without them.
